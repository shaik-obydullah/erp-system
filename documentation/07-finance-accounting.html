Module 07 — Financial Management

Module: Financial Management (Finance)
Category: Accounting
Purpose: Provides a double-entry-style cashbook ledger, a typed transaction log, income and expense tracking, accounts payable/receivable, balances, fixed assets, fiscal years, and multi-currency support.

The cashbook table is the double-entry ledger of the system. Every financial event — sale, fund deposit, expense, payroll, return refund — writes a row. Financial integrity depends on writing these rows atomically with the business transaction that triggered them.

1. Overview

Finance is not an island — it is written to by Sales, Procurement, HRM, Marketing, and Manufacturing. This module documents the shared ledger model and the finance-specific admin surfaces (income, expense, cashbook, payables, receivables, transactions, fixed assets, currencies).

4. Cashbook — Double-Entry Ledger

Cashbook rows are polymorphic: table_name + fk_reference_id point at the source record (sales, incomes, expenses, customers, suppliers, sale_returns…). Four monetary columns describe the movement:

  • in_amount — cash received.
  • out_amount — cash paid.
  • amount_payable — liability created (money owed to suppliers).
  • amount_receivable — receivable created (money owed by customers).

Example writes: POS sale payment → in_amount; sale due → amount_receivable; customer fund → in_amount + amount_payable; return refund → out_amount.

5. Income & Expense

Auto-created — every POS/API sale creates an Income row (description "Sale #INV...") linked to its saleIncome transaction.

Manual entry (admin + API), each wrapped in DB::transaction():

  1. Create Transaction (income / expense) with amount = paid.
  2. Create Income/Expense row referencing the transaction; backfill the transaction's fk_reference_id.
  3. Write the matching Cashbook row (in_amount or out_amount).
  4. Log activity and commit.

Admin routes: GET /incomes + /incomes/create + POST /incomes (incomes.*); GET /expenses + /expenses/create + POST /expenses (expenses.*). API routes: POST /income/save-income, POST /expense/save-expense.

6. Accounts Payable & Receivable

  • Payables (payable table) — supplier liabilities. GET /payables (permission:cashbook.view).
  • Receivables (receivable table) — customer receivables. GET /receivables (permission:cashbook.view).
  • Customer due/fund workflows — CustomerDueController (GET /customers/due), CustomerFundController (deposit & balance). Fund deposit: increments customer balance, writes userFund transaction + cashbook entry, all transactional.
  • Supplier due/fund workflows — SupplierDueController, SupplierFundController.

7. Cashbook & Transaction Viewer

  • GET /cashbook (permission:cashbook.view) — CashbookController; paginated ledger feed with filters.
  • GET /transactions (permission:transactions.view) — TransactionController; full typed transaction log with paid/due amounts.

8. Fixed Assets

GET/POST /fixed-assets + edit/update/destroy — FixedAssetController resource (excluding show). Records name, price, description; acquisitions are tracked in the ledger as fixedAsset transactions.

9. Currencies

  • CurrencyController resource (excluding show) — CRUD over currencies.
  • POST /currencies/{currency}/set-base (permission:settings.save) — marks a currency as the base (rate = 1.000000).

10. Financial Reports

  • ReportController::index — total sales, income (paid), expenses, net profit; 12-month sales vs expenses chart.
  • ReportController::income — date-range income with monthly series.
  • ReportController::expense — date-range expenses with monthly series.
  • ReportController::customer — top customers, balance totals (positive/negative = due).
  • ReportController::supplier — supplier counts + balance totals.
  • API POST /report — YTD vs last-year monthly sales/income/expense for the POS dashboard.

12. Integrity Conventions & Gotchas

  • Every money-moving operation must be wrapped in DB::transaction() with the ledger rows written in the same unit of work. See the canonical examples: ApiController::saveSale, PosController::checkout, CustomerFundController::store, SaleController::receiveDue, SaleReturnController::approve.
  • After any financial mutation, verify a transactions row, an incomes/expenses row (where applicable), and a cashbook row were all written exactly once.
  • Never mutate only the source table (sale/customer/supplier) — keep the ledger in sync.
  • Currency symbols are read via Configuration::get('currency_symbol', '$') across views.
